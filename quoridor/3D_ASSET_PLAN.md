# Quoridor 3D 모델·애니메이션 제작 계획

작성일: 2026-09-18

진행 업데이트 (2026-09-26): Blender MCP로 필수 모델 4종과 캐릭터 애니메이션 6개를 제작하고 GLB로 내보냈다. 통합 원본은 `assets-source/blender/quoridor_assets.blend`, 사용 설명은 `assets-source/README.md`에 있다. 웹 게임 3D 화면에 연결했으며 모의 서버 메시지로 브라우저에서 이동·점프·벽 설치·승패 연출을 검증했다. 실제 서버의 AI·온라인 대전 통합 검증은 미실행이다. 아래 폴더 구조는 초기 계획이고 실제 결과물은 통합 Blender 파일로 관리한다.

## 1. 목표와 기본 방향

현재 웹 기반 Quoridor를 유지하면서 화면을 Three.js 기반 3D로 전환한다. 모델과 캐릭터 애니메이션은 Blender에서 제작하고 GLB로 내보낸다.

이 문서에서 ‘모델’은 게임에 표시되는 3D 에셋을 의미한다. AI 상대는 기존 Python 로직을 사용하므로 별도 생성형 AI 모델이나 학습 작업은 필요하지 않다. AI 상대에게도 플레이어와 같은 캐릭터 모델을 사용할 수 있다.

초기 스타일은 단순한 로우폴리 보드게임으로 가정한다. 카메라는 보드를 내려다보는 고정 사선 시점으로 시작한다. 캐릭터 디자인과 테마는 제작 전에 확정한다.

## 2. 필요한 개수

| 구분 | 최소 플레이 가능 버전 | 권장 완성 버전 |
|---|---:|---:|
| 고유 3D 모델 | 4종 | 6종 |
| Blender 캐릭터 애니메이션 클립 | 3개 | 6개 |
| 코드 기반 연출 | 3종 | 5종 |
| 캐릭터 색상 변형 | 2종 | 2종 |

색상 변형, 복제한 칸과 벽, 벽의 가로·세로 방향은 별도 모델 개수에 포함하지 않는다. 캐릭터는 하나의 모델과 하나의 리그를 공유하고 색상으로 두 플레이어를 구분한다. 배경·카메라·조명은 초기에는 코드로 구성한다.

## 3. 3D 모델 목록

| 번호 | 에셋 | 파일명 | 수량 기준 | 우선순위 | 제작 내용 |
|---|---|---|---|---|---|
| M01 | 보드 받침대 | `board_base.glb` | 고유 모델 1종, 장면에 1개 | 필수 | 외곽 프레임과 바닥. 칸과 벽을 가리지 않는 낮은 형태 |
| M02 | 바닥 칸 | `tile.glb` | 고유 모델 1종, 9×9로 81개 배치 | 필수 | 같은 모델을 반복 배치. 이동 가능 표시가 잘 보이는 단순한 표면 |
| M03 | 플레이어 말 | `pawn.glb` | 고유 모델 1종, 2개 배치 | 필수 | 단순한 캐릭터와 공용 리그. 몸체와 플레이어 식별 색상 영역 분리 |
| M04 | 설치 벽 | `wall.glb` | 고유 모델 1종, 설치 상태에 따라 최대 20개 | 필수 | 두 칸 사이를 막는 길이. 가로·세로는 회전으로 재사용 |
| M05 | 테이블 또는 받침 배경 | `table.glb` | 고유 모델 1종, 장면에 1개 | 선택 | 보드 주변 분위기용. 초기에는 단순 평면으로 대체 |
| M06 | 목표 지점 장식 | `goal_marker.glb` | 고유 모델 1종, 양쪽 끝에 재사용 | 선택 | 깃발·문양 등. 실제 목표는 특정 한 칸이 아닌 끝 행 전체임을 유지 |

두 플레이어를 서로 다른 외형으로 만들 경우 고유 모델은 1종 추가된다. 리그를 공유하면 애니메이션 재사용을 검토할 수 있지만, 비율과 관절 구조가 다르면 별도 수정이 필요하다. 첫 버전은 같은 외형에 두 색상을 적용한다.

## 4. Blender 애니메이션 목록

애니메이션은 `pawn.glb` 안에 이름이 지정된 클립으로 포함한다. 최소 3개, 권장 6개를 제작한다.

| 번호 | 클립 이름 | 용도 | 반복 | 목표 길이 | 우선순위 |
|---|---|---|---|---|---|
| A01 | `Idle` | 가벼운 호흡·흔들림 등 기본 대기 | 반복 | 1.5~2.5초 | 필수 |
| A02 | `Walk` | 인접 칸으로 이동할 때 걷는 동작 | 반복 가능 | 0.4~0.6초 | 필수 |
| A03 | `Jump` | 상대 말을 뛰어넘거나 우회 점프할 때 동작 | 1회 | 0.5~0.7초 | 필수 |
| A04 | `PlaceWall` | 벽 설치 성공 후 짧은 손짓·지시 동작 | 1회 | 0.4~0.7초 | 선택 |
| A05 | `Win` | 목표 행 도착 후 승리 동작 | 1회 | 1.2~2초 | 선택 |
| A06 | `Lose` | 패배 시 아쉬워하는 동작 | 1회 | 1~1.5초 | 선택 |

### 동작 제작 규칙

- 걷기와 점프는 제자리 동작으로 만든다. 보드 위 실제 위치 이동과 점프 높이는 코드가 제어하여 이중 이동을 방지한다.
- 캐릭터 방향 전환은 코드로 처리한다. 상·하·좌·우 걷기를 따로 제작하지 않는다.
- `Jump` 하나를 직선 점프와 대각선 우회 이동에 재사용한다. 코드에서 상대 말 위치와 벽 배치를 고려해 이동 경로를 정한다.
- 대기·이동·승리 동작이 서로 전환되도록 시작·종료 자세를 맞춘다.
- 벽은 원격 위치에도 설치할 수 있으므로 `PlaceWall`을 캐릭터가 설치 위치까지 걸어가야 하는 동작으로 만들지 않는다.
- 최소 버전의 승패는 기존 결과 창으로 표시하고, 벽 설치는 코드 연출로 표현한다.

## 5. Blender 클립이 필요 없는 코드 연출

| 번호 | 연출 | 구현 방향 | 우선순위 |
|---|---|---|---|
| C01 | 칸 사이 이동·방향 전환 | 서버 확정 좌표를 향해 위치와 회전을 보간하고 `Walk` 또는 `Jump` 재생 | 필수 |
| C02 | 벽 설치 미리보기 | 커서 위치에 반투명 벽 표시, 가로·세로 전환. 서버 승인 전까지 확정하지 않음 | 필수 |
| C03 | 벽 등장 | 승인된 벽이 짧게 올라오거나 확대되는 연출 | 필수 |
| C04 | 선택·현재 턴 강조 | 캐릭터 아래 링과 칸의 색상·밝기 변화 | 선택 |
| C05 | 승리 카메라 | 승리 동작에 맞춘 약한 줌·시점 변화 | 선택 |

이동 가능 칸, 학습 모드 평가 색상, 좌표 표시는 별도 Blender 모델 없이 코드로 만든다. 일반 모드에서는 현재 서버가 모든 합법적 벽 위치를 내려주지 않으므로, 정확한 설치 가능/불가능 미리보기까지 구현하려면 서버 조회 또는 추가 판정 로직이 필요하다.

## 6. Blender 제작·내보내기 규격

- 원본은 `.blend`, 웹에서 사용하는 결과물은 `.glb`로 보관한다.
- Blender에서는 Z축을 위로 사용하고, GLB 내보내기의 좌표 변환을 적용한다. Three.js에서는 Y축을 높이로 사용한다.
- 웹 보드의 한 칸 중심 간격을 1단위로 정한다. 초안 기준 칸 너비 0.8, 칸 사이 틈 0.2로 시작한다.
- 캐릭터 높이는 약 0.6~0.8단위, 발밑 원점은 바닥 중앙에 둔다. 실제 시야 검증 후 조정한다.
- 벽 초안은 길이 약 1.8단위, 두께 0.12~0.16단위, 높이 0.3~0.45단위로 시작한다. 받침대의 외곽 여백은 별도로 확보한다.
- 칸·벽·보드의 원점은 바닥 중앙으로 통일한다. 기본 벽은 길이 방향이 Blender X축을 향하도록 만든다.
- 리깅 전에 회전·스케일을 정리한다. 캐릭터 앞 방향은 첫 GLB 가져오기에서 확인하고 모든 클립에서 통일한다.
- 재질은 glTF로 내보낼 수 있는 Principled BSDF와 이미지 텍스처 중심으로 만든다. 복잡한 절차적 재질은 필요하면 텍스처로 베이크한다.
- 제약 조건이나 시뮬레이션에 의존하는 동작은 내보내기 시 지원되는 키프레임으로 베이크하고 결과를 확인한다.
- 초기 성능 예산: 캐릭터 하나 5천~1만 삼각형 이내, 벽·칸은 수백 삼각형 수준, 텍스처는 1K 중심. 실제 기기 테스트로 조정한다.
- 캐릭터 2개는 서로 독립적으로 애니메이션을 재생할 수 있도록 리그 복제와 재생기를 구성한다.
- Blender 화면과 웹 화면의 조명·색감은 다를 수 있으므로 웹에서 최종 확인한다.

## 7. 권장 폴더 구조

아래는 향후 제작 시 사용할 구조이며, 현재 문서 작성 단계에서 에셋 파일이 생성된 것은 아니다.

```text
assets-source/
  blender/
    board.blend          # 받침대와 칸 원본
    pawn.blend           # 캐릭터, 리그, 애니메이션 원본
    wall.blend           # 벽 원본
    environment.blend    # 선택 배경과 목표 장식 원본
  textures/              # 편집용 텍스처 원본
web/
  assets/
    models/
      board_base.glb
      tile.glb
      pawn.glb           # Idle, Walk, Jump 및 선택 클립 포함
      wall.glb
      table.glb          # 선택
      goal_marker.glb    # 선택
```

원본과 내보낸 파일을 구분해 친구 저장소에서도 수정 가능하도록 관리한다. 대용량 원본이 생기면 업로드 전에 Git LFS 사용 여부를 결정한다.

## 8. 구현 순서와 완료 기준

### 1단계: 기본 도형으로 3D 게임 연결

- `web/board.js`에서 보드 렌더링·입력 처리를 메뉴와 HUD 처리에서 분리한다.
- Three.js 장면, 카메라, 조명, 클릭 판정을 구현한다.
- 기존 `move`, `place_wall` 메시지 형식과 서버 규칙을 유지한다.
- 기존 서버 상태의 행·열을 3D X/Z 위치로 변환한다.
- AI 대전, 두 브라우저의 온라인 대전, 점프, 벽 설치, 승리 판정을 확인한다.

완료 기준: 임시 도형으로 기존 게임을 끝까지 플레이할 수 있다.

### 2단계: 필수 모델 4종 연결

- M01~M04를 제작하고 GLB로 내보낸다.
- 임시 도형을 교체하고 크기·원점·재질을 검증한다.
- 말 2개의 색상을 구분하고, 벽이 뒤쪽 칸과 말을 과하게 가리지 않는지 확인한다.

완료 기준: Blender에서 만든 모델로 게임이 동작하며 클릭 위치와 표시 위치가 일치한다.

### 3단계: 필수 애니메이션 3개와 코드 연출 3종 연결

- A01~A03과 C01~C03을 연결한다.
- 서버가 승인한 상태를 기준으로 연출한다. 거절된 이동·벽은 확정 연출하지 않는다.
- 이전/새 상태를 비교해 이동한 말과 새로 설치된 벽을 판별한다.
- 애니메이션 중 도착한 다음 상태를 순서대로 처리한다. 초기 상태 수신에서는 과거 이동을 재생하지 않는다.
- 연속 클릭으로 중복 요청이 발생하지 않도록 입력을 관리한다.

완료 기준: AI와 온라인 모드에서 표시 위치·실제 상태가 어긋나지 않고 한 판을 끝낼 수 있다.

### 4단계: 선택 에셋과 마감

- M05~M06, A04~A06, C04~C05를 추가한다.
- 학습 모드 평가 색상·호버 설명·좌표 표시를 3D 화면에 연결한다.
- 채팅과 메뉴, 화면 크기 변경, 작은 화면에서의 가독성과 성능을 확인한다.

완료 기준: 기존 기능을 유지하면서 시야·조작·애니메이션이 자연스럽게 동작한다.

## 9. 첫 제작 범위

먼저 제작할 것은 **모델 4종(보드 받침대·칸·캐릭터·벽), 캐릭터 애니메이션 3개(Idle·Walk·Jump), 캐릭터 색상 2종**이다. 필수 코드 연출은 **이동·회전, 벽 미리보기, 벽 등장**의 3종이다.

이 구성이 정상 동작한 후 권장 완성 범위인 모델 6종·캐릭터 애니메이션 6개·코드 연출 5종으로 확장한다. 실제 일정은 캐릭터 디자인과 목표 품질을 확정한 뒤 산정한다.
